LWC CODE PATTERN
================

Use this to reformat any existing Lightning Web Component (LWC) so it follows the house code
pattern. The behaviour, the design and the events it sends stay exactly the same; only the
layout, the file split, the comments and the naming change.
For Apex classes use docs/04_CLASS_CODE_PATTERN.txt instead.

The aim: a junior Salesforce developer can open any component and understand it without help.
Prefer more variables, more small steps and plain names over short, clever code.

PROMPT TO REUSE
---------------
"Rewrite the <componentName> LWC to follow docs/05_LWC_CODE_PATTERN.txt.
Keep the same behaviour, design and events, change only the code pattern. Only touch the
files in force-app/main/default/lwc/<componentName>/."

REFERENCE EXAMPLE
-----------------
force-app/main/default/lwc/aiChatWorkingIndicator/ (has no Helper: its logic is short enough to stay in the controller)

RULES
-----
1. Files in the component folder
   - <name>.js           The controller: what the component does. No hard-coded values and no
                         long logic in here.
   - <name>Settings.js   Pure settings: constants, label text, class names, status values.
                         No functions, no logic, no imports of other files.
   - <name>Helper.js     The extended methods: plain exported functions with no component state.
                         Only create it when the controller has logic worth moving out.
   - <name>.html         The template.
   - <name>.css          Only when SLDS cannot do the job (see rule 8).
   - <name>.js-meta.xml  Unchanged.
   - Each component owns its own Settings and Helper. Never create a shared utils component
     that many components import; a small amount of repeated code is the price of that.
   - Files inside a component are imported with a relative path: "./<name>Settings".

2. Header comment (on the controller, the Settings file and the Helper file)
   - Component Name, Description, then the version table.
   - The Description is a short one-line summary, then the high-level workflow as numbered steps:
     "Step 1: ...", "Step 2: ...", one short plain-English line each, in the order they happen.
   - Version table has three columns: Version, Author, Description (no date column).
   - Remove every existing version row. The table always has exactly one row, never added to:
     1.0          Chandler Stuart          Initial development

3. Settings file (<name>Settings.js)
   - Every value the controller would otherwise type in by hand lives here: label text,
     status and mode names, CSS class names, icon names, sizes, timings, limits, patterns.
   - Group the values under a plain-English comment (a "section" comment), one blank line between groups.
   - UPPER_SNAKE_CASE for constants, camelCase for the keys inside a label object.
   - Values that mirror Apex or a picklist say so in the comment, naming the Apex constant or field.
   - Static attributes written in the HTML (an icon name on lightning-icon, for example) stay in
     the HTML. Do not push them through the controller just to avoid typing them.

4. Helper file (<name>Helper.js)
   - Only exported functions that take everything they need as parameters and return a result.
   - No this, no component state, no events, no calls to Apex.
   - A comment directly above each function says what it does, in one plain sentence.
   - Number the steps inside a function: "// [1] What this does". Sentence case, no jargon.
     Numbers run in order through the function; the next function restarts at [1].

5. Controller layout (<name>.js)
   - JavaScript is formatted by hand, like Apex. 2-space indent. Do NOT run Prettier on a
     component that follows this pattern: add its .js files to .prettierignore.
   - An import goes on ONE line, however many names it brings in.
     Wrong:
         import {
           LABELS,
           MODE_STEPS
         } from "./aiChatExampleSettings";
     Right:
         import { LABELS, MODE_STEPS } from "./aiChatExampleSettings";
   - Never split a statement over several lines: calls, objects with a few entries, conditions
     and assignments all stay on one line.
   - Leave a blank line after the opening brace of the class, of every getter and method,
     and of every multi-line loop or if block.
   - Leave a blank line between logical blocks (inputs, building, returning).
   - Order: imports, header comment, class comment, @api properties, tracked state,
     lifecycle methods (connectedCallback...), getters, event handlers, private methods.
   - A short comment above each group says what the group is for, e.g.
     "// Values passed in by the parent component".
   - A comment on each @api property says what the parent should pass and the allowed values.
   - Getters and methods stay short. If one needs more than a handful of lines, move the
     work into a function in the Helper file and call it.
   - Use the same numbered steps comment style as the Helper ("// [1] ...").

6. Variables and naming
   - Put every step in its own named variable instead of chaining or nesting expressions.
     Wrong:  return (this.steps || []).map((step) => ({ ...step, isDone: step.state === DONE }));
     Right:  const steps = this.steps || [];
             const isDone = step.state === STEP_STATE_DONE;
   - Names say what the thing is, in full words: stepViews, not sv; isDone, not d.
   - Booleans start with is, has, show or can: isSteps, hasMore, showHeader.
   - Event handlers start with handle: handleSend, handleClose.
   - Getters that feed the template are nouns or booleans: stepViews, isSteps, buttonClass.
   - Helper functions start with a verb that says what the caller gets:
       get     - read something that already exists and return it (getCopyLabel)
       build   - assemble a new value from other values (buildStepViews)
       find    - search, and return null when there is no match (findLastIndex)
       is/has  - answer true or false (isSameId)
       format  - turn a value into display text (formatElapsed)
     Never name a function toXxx or assertXxx.
   - No magic values in the controller or Helper: if it is a literal that means something
     (a status, a class name, a number), it goes in the Settings file with a name.
   - Keep the HTML property names the template already uses so the template does not break.

7. HTML (<name>.html)
   - Use SLDS as much as possible without changing the current design or function:
     slds-grid, slds-col, slds-box, slds-p-*, slds-m-*, slds-text-*, slds-border_*,
     slds-theme_*, and the lightning-* base components (lightning-icon, lightning-button...)
     in place of hand-drawn markup or custom classes.
   - Every element sits on ONE line, with all of its attributes on that line, however long.
     Wrong:
         <lightning-icon
           icon-name="utility:success"
           variant="success"
         ></lightning-icon>
     Right:
         <lightning-icon icon-name="utility:success" variant="success" size="xx-small" class="slds-m-right_small"></lightning-icon>
   - A comment above each section of the template says in plain English what it shows
     and when: <!-- Step card: shown when the trace is on -->
   - Computed class names and text come from the controller; the template holds no logic.
   - Prettier would wrap long lines, so each component that follows this pattern gets an
     override in .prettierrc with a large printWidth for its own .html file, and its .js
     files are listed in .prettierignore.

8. CSS (<name>.css)
   - Every component's CSS file owns ALL the styles its own template uses. Never share a
     stylesheet between components: no "@import" of another component, and no shared
     styles component (aiChatStyles was deleted for this reason). If two components need the
     same rule, each one holds its own copy.
   - A child component's styles are never put in its parent's CSS: LWC styles do not reach
     into a child component, so each child styles itself.
   - Delete a rule when an SLDS utility class can do it in the HTML.
   - Keep only what SLDS cannot do (an animation, a design-token colour, a small custom look).
   - Colours come from the --aia-* design tokens; the page-level tokens are defined once on the
     root component (aiAssistChat) and inherit into every child. No new hard-coded colours.
   - A comment above EVERY section says in plain English what it styles and why it is custom:
     /* Makes the loading icon turn. SLDS has no utility for this. */
     That includes @keyframes and @media blocks.
   - One blank line between sections.

9. Do not change
   - Behaviour, @api names, event names and their detail, or what the component looks like.
   - The .js-meta.xml.
   - If a pasted or older version of the component differs from the file in the repo,
     keep the repo's behaviour and apply only the pattern.
   - Where SLDS gives a slightly different look (radius, spacing), keep the SLDS version and
     list the visible differences in your reply so they can be checked in a browser.

SKELETON
--------
Controller (<name>.js):

/*
Component Name: aiChatExample

=================================================================
=================================================================

Description: One-line summary of what the component does.

Step 1: What it shows or does first
Step 2: What it does when the user acts
Step 3: What it tells the parent

=================================================================
=================================================================

Version      Author                   Description
1.0          Chandler Stuart          Initial development
*/

import { LightningElement, api } from "lwc";
import { LABELS, STATUS_DONE } from "./aiChatExampleSettings";
import { buildItemViews } from "./aiChatExampleHelper";

export default class AiChatExample extends LightningElement {

  // Values passed in by the parent component
  @api items = []; // [{ label, status: 'done' | 'pending' }]

  // Values the template reads
  labels = LABELS;

  // The items turned into what the template needs.
  get itemViews() {

    // [1] Hand the work to the helper
    return buildItemViews(this.items);
  }
}

Helper (<name>Helper.js):

import { STATUS_DONE } from "./aiChatExampleSettings";

// Turns each item from the parent into the values the template needs.
export function buildItemViews(items) {

  // [1] The parent may not have set any items yet
  const itemList = items || [];
  const itemViews = [];

  // [2] Build one view per item
  itemList.forEach((item, index) => {
    const isDone = item.status === STATUS_DONE;
    itemViews.push({ key: index, label: item.label, isDone });
  });

  return itemViews;
}
