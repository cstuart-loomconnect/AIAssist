AI PROVIDER 3: ANTHROPIC AGENT API (MANAGED AGENTS, BETA)
==========================================================

The third AI provider, beside Anthropic (Messages API) and OpenAI (Chat Completions). Picklist value
AIModelConfiguration__c.AIProvider__c = AnthropicAgent, label "Anthropic Agent API".

Status: first version, written against Anthropic's Managed Agents beta (header managed-agents-2026-04-01).
Not yet run in an org: see section 9 before relying on it.


1. WHY IT IS A DIFFERENT PROVIDER
---------------------------------
The Messages API is stateless. Each call carries the whole conversation, the model, the tools and the system
prompt, and one POST gets one reply.

The Agent API is stateful and event based. Anthropic keeps the agent and runs its loop:
  - The AGENT (model, system prompt, tools) is created once in Anthropic and referred to by id (agent_...).
  - The ENVIRONMENT (the container the agent works in) is created once and referred to by id (env_...).
  - A SESSION is one run of an agent in an environment (sesn_...).
  - You POST EVENTS to a session (user.message, user.custom_tool_result, ...) and READ EVENTS back
    (agent.message, agent.custom_tool_use, session.status_idle, ...).

So one question needs several callouts. The provider contract stays the same (a request builder and a response
handler), with two small additions so the pair can share a session:
  - AIProvider.Request carries endpoint, environmentId, maxWaitMilliseconds and a session.
  - IAIProviderResponseHandler.handleResponse receives the request that produced the response (last argument,
    null when only tool results are being added). The Messages and OpenAI handlers ignore it.


2. HOW ONE TURN RUNS
--------------------
AIAgentManager.executeAiMessage keeps its loop: build request, send, read reply, run tools, repeat. It makes one
AIProvider.Session per turn and puts it on every request. The session starts empty.

  Request builder (AIAnthropicAgentRequestBuilder)
    - session empty (first pass): POST /v1/sessions for the agent and environment, then record the session's
      events endpoint and the anthropic-beta header on the session.
    - build { events: [...] } for the last message.
  AIAgentManager
    - POSTs the body to the session's events endpoint (instead of the Named Credential + API Path), with the
      session's headers.
  Response handler (AIAnthropicAgentResponseHandler)
    - the POST response only says the events were accepted, so it fetches GET .../events again and again until
      the session is idle or ended, the time runs out, or callouts run low.
    - reads agent.message text into the reply, agent.custom_tool_use into tool calls, and usage into tokens.
  AIAgentManager
    - agent.custom_tool_use?  run the data source and loop: the next events body is one
      user.custom_tool_result per call, sent to the same session.
    - no tool calls?  the agent.message text is the reply.

What each class does:
  AIAnthropicAgentRequestBuilder   Session start. Last message is a user message: [system.message with the
                                   assembled system prompt] + user.message (earlier turns written into the text).
                                   Last message is tool results: one user.custom_tool_result per result.
                                   Also holds sendRequest, the one place Agent API callouts get their headers.
  AIAnthropicAgentResponseHandler  Event fetch loop, time limit, interrupt. agent.message -> reply.
                                   agent.custom_tool_use -> ToolCall (id = event id). span.model_request_end
                                   model_usage -> tokens. Errors, ended sessions and approval waits -> exception
                                   with a message saying what to change.
  AIProvider                       Registers the builder and handler and the preset; defines Request and Session.
  AIAgentManager                   Makes the session, fills the Request, sends to the session endpoint.


3. WHAT AN ADMIN SETS UP
------------------------
In Anthropic (once, outside Salesforce; see the Managed Agents docs or the claude-api skill):

  a. Create an ENVIRONMENT                POST /v1/environments           -> env_...
  b. Create an AGENT                      POST /v1/agents                 -> agent_...
       - model and system prompt: the agent's own base behaviour.
       - tools: add one "custom" tool per AIDataSource__c the agent should use. The tool name MUST equal
         AIDataSource__c.DeveloperName__c and input_schema should match AIDataSource__c.InputSchema__c.
         The model configuration cannot send tools; the agent holds them.
       - permission policy: always_allow or auto. Built-in tools set to always_ask pause the session waiting
         for approval, which this package cannot give, and the turn fails (the error says so).
       - web_fetch and web_search: leave disabled unless the agent needs the web.
       - model: must support system.message (Claude Opus 5.5, Opus 5, Opus 4.8, Sonnet 5.5, Haiku 5.5,
         Fable 5 / 5.1, Mythos 5 / 5.1; not Sonnet 5). Otherwise the system prompt event is rejected.

In Salesforce:

  c. External Credential / Named Credential for https://api.anthropic.com, header x-api-key from the API key.
     AIProvider.getPreset(AnthropicAgent) gives the starting values (the anthropic-beta header is added from the
     session, not the credential).
  d. AI Model Configuration:
       AI Provider          Anthropic Agent API
       Named Credential     the credential from step c
       API Path             /v1/sessions
       Model Identifier     the agent id (agent_...)
       Environment Id       the environment id (env_...)          (new field EnvironmentId__c)
       API Version Header   anthropic-version / 2023-06-01
     Maximum Output Tokens and Temperature are ignored: they belong to the agent.
  e. Set AIAssistSettings__c.CalloutTimeoutMilliseconds__c to how long one request may wait for the agent
     (see section 5).


4. WHAT THE AGENT SEES
----------------------
  - System prompt: the agent's own prompt, plus AI Assist's assembled prompt (persona, template, language,
    workflow action instructions) sent as a system.message at the start of each turn.
  - History: each turn starts a NEW session. Earlier messages of the conversation are written into the first
    user.message as "Conversation so far: User: ... Assistant: ...", followed by "Latest user message:".
  - Tools: the agent's own custom tools, answered by AIDataSourceDispatcher exactly as for the other providers
    (same PII masking, same step tracking, same limits). A tool the agent calls that is not an AI Assist data
    source gets the usual "unknown tool" failure result.
  - Built-in agent tools (bash, file editing) run in Anthropic's container and never touch Salesforce.
  - Last tool-calling iteration: the "do not call a tool" instruction (tool_choice none) does not exist in the
    Agent API. AIAgentManager already stops the loop in that case.


5. LIMITS TO KNOW BEFORE USING IT
---------------------------------
  Time        Apex cannot hold a stream open or sleep between calls, so the response handler fetches the event list again
              straight away. A request must finish inside CalloutTimeoutMilliseconds__c (and Salesforce allows 120
              seconds of callout time per transaction). Past that the agent is sent user.interrupt and the turn
              fails with a provider error (not retried). Suits short agent runs, not long research tasks.
  Callouts    Every event fetch is a callout and a transaction may make 100. The handler stops fetching when
              five are left. A turn that needs many tool passes plus slow answers can hit this.
  Cost        Agent runs are billed per token plus session running time, and the agent may make several model
              requests per turn. Tokens reported are the sum of span.model_request_end usage (cache tokens
              counted as input). Running time is not reported in tokens.
  Sessions    A session is created per turn and never archived or reused, so sessions accumulate in the
              Anthropic console. They are disposable.
  Data        Everything the agent reads is sent to Anthropic, as with the other providers. Anything the agent's
              own tools or MCP servers read never passes through AI Assist's masking.
  Beta        Anthropic may change event names and shapes. All names are constants prefixed ANTHROPIC_AGENT_ in
              AIAssistApplicationConstants.

            field, in the model configuration layout and the AIAssistAdminUser / AIAssistSuperUser permission sets).

To add a further provider of this kind: implement the builder and handler, add the picklist value and constant,
add a line to each map in AIProvider. A provider that needs several callouts keeps its state on
AIProvider.Session, which the manager makes once per turn.


7. REQUEST AND RESPONSE SHAPES
------------------------------
Start a session (request builder):
  POST callout:<NamedCredential>/v1/sessions
  { "agent": { "type": "agent", "id": "agent_..." }, "environment_id": "env_..." }
  -> { "id": "sesn_...", ... }

Send events (request builder output):
  POST .../v1/sessions/{id}/events
  { "events": [
      { "type": "system.message", "content": [ { "type": "text", "text": "<assembled system prompt>" } ] },
      { "type": "user.message",   "content": [ { "type": "text", "text": "<message>" } ] } ] }
  After a custom tool call:
  { "events": [ { "type": "user.custom_tool_result", "custom_tool_use_id": "<agent.custom_tool_use id>",
                  "content": [ { "type": "text", "text": "<result>" } ] } ] }

Read events (response handler):
  GET .../v1/sessions/{id}/events  -> { "data": [ ...events in order... ] }
  The handler keeps the events after the LAST user.message / user.custom_tool_result, and stops when one of
  them is session.status_idle or session.status_terminated.

What the response handler is given: the HTTP response of the events POST (only checked for success) and the
request, whose session says where to fetch. A failed POST is dealt with by AIAgentManager like any other
provider failure (AIProvider.getFailureReason, retry rules). A failed session start is thrown by the request
builder, so it is logged as a failure of the turn without those mappings.
